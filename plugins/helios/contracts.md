# Contracts register

Every interface that crosses a repository boundary in the Helios estate, and every engine
contract that a feature not yet designed must honour because an existing specification
already consumes it. A spec cites a contract by its name and version here; the
`contracts-register` skill has the rules for changing one.

| Contract | Owner | Version | Specification | Consumers | What it is |
|---|---|---|---|---|---|
| Door wire protocol | HeliosDoorKit | none yet | HeliosDoorKit `docs/` | HeliosDoors (host side), every door built with the kit | How a door and its host exchange screens and input, front-end independent |
| Door hosting protocol | HeliosDoors | none yet | HeliosDoors `docs/` | HeliosAdvance, any other BBS software that supports it | How a BBS hands a caller to a hosted door and gets them back; the engine never launches a door itself |
| Door admin interface | HeliosDoors | none yet | HeliosDoors `docs/` | HeliosAdvance (`hadv-config`, `hadv-config-gui`) | How an administration tool configures a `hadv-doors` instance remotely, with its own credentials, separate from the hosting protocol |
| Public JSON API | HeliosAdvance | none yet | HeliosAdvance `docs/spec/` and its OpenAPI description | HeliosPortal, HeliosLoadTest | The board's HTTP interface for clients |
| Terminal surfaces | HeliosAdvance | public standards | RFC 854 (Telnet), RFC 4253 (SSH) | HeliosSIP, HeliosLoadTest | Nothing Helios-specific: a SIP caller or a load driver is an ordinary Telnet or SSH client |
| Server health (`cluster.health` v1) | HeliosAdvance | 1 | HeliosAdvance `docs/spec/` (cluster) | a proxy in front of the board, HeliosLoadTest | each server's health and utilisation over HTTP, detailed only to the trusted proxy list |
| access-control v1 | HeliosAdvance | 1 | HeliosAdvance `docs/spec/` (access-control) | every engine gate | the one authorisation check and its principals |
| sessions v1 | HeliosAdvance | 1 | the feature that provides sessions publishes it; until then the operations the engine's documents state are the contract | cluster, access-control | session identifiers (unpredictable, unique across servers), a session's end per surface, per-account concurrent-session limits, and caller display names |
| theme v1 | HeliosAdvance | 1 | the feature that provides themes publishes it; until then the operations the engine's documents state are the contract | cluster | the busy and "not accepting callers" screens |
| join v1 | HeliosAdvance | 1 | the feature that provides the join publishes it; until then the property the engine's documents state is the contract | cluster | carrying the key-encryption key and a new server's bootstrap record to a joining host over the paired channel it owns, never through the database, and calling addServer on the sysop's behalf; the pairing code is created only through admin-api v1 by an operator account holding `board.administer`, which the join's addServer names as its actor |
| accounts v1 | HeliosAdvance | 1 | the feature that provides accounts publishes it; until then the operations the engine's documents state are the contract | admin-api, sessions | resolving an account, verifying a password with the board-wide lockout and source slowdown, and the revocation obligation |
| admin-api v1 | HeliosAdvance | 1 | HeliosAdvance `docs/spec/` (admin-api) | `hadv-config`, `hadv-console` and the later administration tools, and their graphical counterparts | the Admin API over HTTP/1.1 and TLS 1.3: sign-in, credentials, settings, the allow list, the registry, audit, actions |
| sessions.operator v1 | HeliosAdvance | 1 | HeliosAdvance `docs/spec/` (sessions) | admin-api, cluster; the features providing accounts v1, rbac v1 and second-factor v1, which must call its revocations | operator credentials: issue, verify, end, revoke, revoke for an account or a server |
| rbac v1 | HeliosAdvance | 1 | the feature that provides roles publishes it; until then the operations the engine's documents state are the contract | access-control, admin-api | an account's roles, a role's members, what a role grants; its obligations on revocation and on the remote-administration policy |
| second-factor v1 | HeliosAdvance | 1 | the feature that provides the second factor publishes it; until then the operations the engine's documents state are the contract | admin-api | whether an account needs a second factor, the challenge and the verification; its obligations on revocation and the policy |
| certificates v1 | HeliosAdvance | 1 | the feature that provides certificates publishes it; until then the operations the engine's documents state are the contract | admin-api | the board identifier, the board signing key and mode, and each server's Admin API chain |
| review question set v1 | HeliosSkills | 1 | HeliosSkills `docs/spec/` (review-questions) | the round runner in HeliosTools `work`; each reviewed repository writes its own at `.helios/review-questions.json` | how a repository declares what a whole-codebase review of it asks: its review groups, finding classes and questions |
| review round v1 | HeliosSkills | 1 | HeliosSkills `docs/spec/` (review-rounds) | HeliosTools (`work`), the loop in HeliosAdvance `automation/`, the scheduler in HeliosBBS/.github | the round issue and fix issue shapes, the tier tags, the agent output formats, the review mode's contract, and the open, select, step, triage and mint operations |
| review results v1 | HeliosSkills | 1 | HeliosSkills `docs/spec/` (review-results) | HeliosTools (`work`), the release check in HeliosBBS/.github, the results repository HeliosReviews | the records every round writes to the results repository, the conditional update, the developer authorship check, and the release gate's state |
| VirtualNET wire format | separate specification | none yet | supplied ahead of the transport's implementation | HeliosAdvance | The frozen store-and-forward network format; the constitution's standing exception |
